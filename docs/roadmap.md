# Roadmap

README 只描述 ReMi 当前 MVP：高质量锚定，以及基于锚点像本体回答。

下面这些方向重要，但不属于当前 MVP 边界。

## 主动调度

ReMi 不应该只是一个被动应答的分身。长期来看，分身还应该能够围绕目标持续主动推进工作。

这里的核心不是“自动执行一串脚本”，而是**目标管理 + 主动调度**：

- 用户为分身设定长期目标，目标采用树形结构组织
- 分身被唤起时，从根目标开始，选择当前最有价值的一条路径继续推进
- 每次激活都可以局部维护目标树，例如创建新任务、关闭失效节点、重排优先级

## 执行层

ReMi 本身不直接承担所有执行细节。长期版本中，会存在一个独立的执行层进程，对外暴露 Base URL / API：

- ReMi 通过执行层 API 查询 Session 状态
- 可执行任务的实际载体是外部 Session
- 分身推进任务时，会读取 Session history，并向 Session 追加新的 prompt input
- 如果当前路径下没有合适 Session，分身可以自主创建新的 Session 并启动第一轮推进

这让 ReMi 保持“调度中枢”的角色：负责决定下一步做什么、为什么做；执行层负责把动作真正跑起来。

## 进度更新

主动调度里一个重要约束是：**进度不能由分身自己主观打分**。

分身可以定义评价标准、注入测试思路、要求执行层按某种流程验证，但真正的进度更新必须来自可验证的执行结果，例如测试通过率、结构化检查结果、明确的完成信号。

## 思考预算

主动调度不是无限免费算力，而是受预算约束的持续循环：

- **用户预算**：用户购买自己的思考预算，在预算内持续推进目标
- **平台预算**：平台提供免费预算，通过公平轮转方式在所有用户之间分配推进机会

两套预算长期会并行存在，但它们不改变当前 MVP 的定义。
