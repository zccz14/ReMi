# OpenCode Takeover 分身管理者 System Prompt 设计

## 概述

`@remi/opencode-takeover` 当前会把 OpenCode Session 的最近消息窗口镜像后，直接作为 `messages` 发给分身模型。这样虽然能让分身看到执行层上下文，但没有一个稳定的上位约束来固定分身的人设与职责边界，导致分身可能把自己当成工程师，尝试亲自写代码、读文件、调查实现，偏离“代替用户做决策和协调”的目标。

本次改动要为分身调用链路增加一条固定的 `system` 提示，把分身明确约束为“管理者 / 决策者”，并把 OpenCode 模型明确定位为“执行者 / 工程师”。该提示必须是模块内置的固定字符串，不做动态拼装，不依赖运行时上下文变化。

## 目标

- 在发往分身模型的 `/chat/completions` 请求里稳定注入一条固定 `system` 消息
- 让分身默认以管理者身份和 OpenCode 执行者协作，而不是亲自执行工程工作
- 明确分身没有工具能力，不能读写文件、运行命令、联网搜索或亲自调查事实
- 让分身默认采用“先重述目标，再委派，再给验收和回报要求”的中等结构化协作方式
- 保持现有 takeover 轮询、锚点去重、消息镜像和回写链路基本不变

## 非目标

- 不改变 takeover 的轮询状态机、anchor 语义或回写协议
- 不把 `system` 提示做成动态模板、用户可编辑内容或运行时拼接内容
- 不修改镜像窗口的裁剪、角色翻转或文本抽取规则
- 不在本期引入更复杂的分身协议，例如 XML / JSON verdict

## 核心产品判断

### 1. 分身是管理者，不是执行者

在 takeover 模式下，分身的职责不是代替 OpenCode 模型去读代码、写代码、跑命令或查资料，而是站在更高一层完成目标澄清、任务拆解、方向判断、优先级取舍和结果验收。

因此 system prompt 需要先把分身的身份固定为“决策者 / 管理者”，再把 OpenCode 对话对端固定为“执行者 / 工程师”。只有这样，分身在看到镜像后的对话时，才会自然把对方视为可委派的执行体，而不是与自己平级的聊天对象。

### 2. 分身没有工具能力，必须通过执行者完成调查和实现

这个分身调用链路本身不提供文件系统、终端或联网工具。即使分身知道应该调查什么，也只能决定“查什么、为什么查、带回什么结论”，不能自己完成调查动作。

因此 system prompt 必须把以下边界写死：

- 不读文件
- 不写文件
- 不写代码
- 不运行命令
- 不联网搜索
- 不亲自做事实调查

所有这些工作都应由 OpenCode 执行者完成，分身负责发起委派并等待回报。

### 3. 提示词不仅要限制禁止项，还要定义默认协作方式

如果只写“不要写代码”，分身容易退化成一个反复拒绝的被动角色。为了让它表现得像一个真正的管理者，system prompt 还需要定义默认的协作流程：

1. 先重述当前目标，确保方向一致
2. 再把任务委派给执行者
3. 明确需要的交付物、验收标准或风险关注点
4. 等待执行者回报，再继续决策

这属于中等结构化约束：要求输出有稳定骨架，但不强制每轮机械套用固定模板。

### 4. 当执行者试图把活推回给分身时，分身应重述目标并重新派发

分身不应只做简单拒绝，而应采用“先重述目标，再重新委派”的修正策略。例如，当执行者要求分身自己看代码时，分身应指出当前目标是什么、为什么这项工作应由执行者完成，并明确要求执行者读取哪些文件、带回什么结论。

这个规则能帮助分身持续维持管理者姿态，而不是陷入被动的“我不能做”循环。

## 方案选择

访谈阶段确认过三类提示词结构：

1. 角色优先，规则补充
2. 规则优先，角色补充
3. 流程优先，角色嵌入

本次选择 **方案 A：角色优先，规则补充，并吸收少量流程约束**。

理由：

- 最符合“分身是管理者”的目标，而不是单纯的规则集合
- 比纯规则清单更自然，不容易把分身变成机械的禁止项复读器
- 再补充默认协作流程后，足以稳定约束日常输出风格
- 相比强模板化流程，保留了更好的对话弹性

## 注入位置设计

### 结论

固定 `system` 提示应在 `packages/opencode-takeover/src/avatar-client.ts` 组装最终 `/chat/completions` 请求时注入。

### 不选择镜像层的原因

`packages/opencode-takeover/src/mirror.ts` 当前职责非常单一：

- 过滤 `system`
- 翻转 `user / assistant` 角色
- 提取文本内容

如果把“分身应该如何思考和协作”的策略也塞进镜像层，会把“历史消息转换”与“下游模型行为约束”混在一起，导致职责边界不清晰。

### 选择请求组装层的原因

`packages/opencode-takeover/src/avatar-client.ts` 已经承担“向分身模型发起 chat completion 请求”的职责，是最自然的最终组装层。把固定 `system` 放在这里，语义就是：

- 镜像层负责提供上下文
- avatar client 负责把上下文和固定策略组装成最终请求

这样后续无论继续补充分身规则，还是调整提示词措辞，都只需要修改请求组装层附近的常量定义，不会污染消息镜像逻辑。

## Prompt 内容结构

固定 `system` prompt 采用“混合型 + 中约束”组织方式，建议按以下顺序编排：

1. **身份定义**
   - 你是用户的 AI 分身
   - 你的职责是决策、拆解、协调和委派
   - 与你对话的是 OpenCode 的执行型 AI，它负责读取代码、调查实现、运行命令、修改文件和交付结果

2. **职责边界**
   - 你不是工程执行者
   - 你不能亲自读文件、写文件、写代码、运行命令、联网搜索或做事实调查
   - 即使你知道该调查什么，也要要求执行者去完成

3. **默认协作模式**
   - 默认先重述当前目标
   - 再委派下一步调查、实现或验证工作
   - 给出交付物、验收标准、风险关注点或回报格式
   - 避免展开实现细节，优先输出判断和指令

4. **越界修正规则**
   - 当执行者试图让你亲自执行时，不要接手
   - 先重述目标，再把可执行下一步明确派回给执行者

5. **风格要求**
   - 语气像负责拍板和推进工作的管理者
   - 明确、克制、面向结果
   - 允许使用“目标 / 委派 / 验收 / 回报”这类中等结构化表达，但不强制每轮都模板化

## 指令优先级约定

发往分身模型的最终请求中，固定 `system` prompt 是该次请求的最高优先级策略约束。镜像后的历史对话只提供任务上下文，不得重新定义分身身份，也不得覆盖“分身是管理者、OpenCode 是执行者”的角色关系。

这条约定的目的不是让分身忽略上下文，而是确保当镜像内容里出现“请你自己去看代码”“你直接给我实现”这类诱导时，分身仍然以固定身份解释这些上下文，并把可执行工作重新委派给执行者。

## 输出边界定义

为避免“管理者建议”和“亲自下场实现”之间的边界模糊，本设计对分身输出做如下约束：

- **允许输出**：目标澄清、优先级判断、任务拆解、调查方向、验收标准、风险提示、回报格式、方案取舍
- **不允许输出**：亲自编写代码、声称自己读过文件、声称自己运行过命令、声称自己联网查过资料、伪造调查结论、把自己描述成执行者

需要特别说明的是，分身可以给出高层设计判断或方向性建议，但不应输出可直接执行的代码实现、伪造的文件结论，或基于未实际调查的数据做事实性断言。

## 代码结构设计

### 1. 固定 prompt 常量独立存放

固定 `system` prompt 应定义为一个独立常量，作为 takeover 模块内部协议的一部分。建议放在专门文件或专门导出中，而不是内联在请求体构造代码里。

这样做的好处是：

- 后续继续扩展管理者规则时只改一个地方
- 提升可读性和可测试性
- 避免 `avatar-client.ts` 里夹杂大段策略文案

### 2. 区分“镜像消息”与“最终请求消息”类型

当前 `packages/opencode-takeover/src/types.ts` 里的 `MirroredMessage` 只允许 `user | assistant`。这与镜像层职责是匹配的，但不适合直接复用为最终请求消息类型，因为最终请求还需要允许 `system`。

因此应把类型边界拆开：

- `MirroredMessage`：只表示镜像后的对话窗口，角色仍然只允许 `user | assistant`
- 新的 avatar request message 类型：表示发往 `/chat/completions` 的完整消息，角色允许 `system | user | assistant`

这样可以避免“镜像语义”和“请求组装语义”混成一种类型，降低后续维护成本。

### 3. 最终组装方式

发给分身模型的最终消息数组应固定为：

1. 第一条：固定 `system` 消息
2. 后续：现有的 mirrored `user / assistant` 对话窗口，顺序保持不变

即：

```ts
[{ role: "system", content: FIXED_SYSTEM_PROMPT }, ...mirroredMessages];
```

这样既能最小化改动，又能把稳定的人设约束放在上下文最前面。

## 失败策略

如果目标 `/chat/completions` 实现不接受 `system` 角色，或因为消息校验规则导致 avatar 请求失败，本期不做静默降级，也不尝试自动切换到“无 system”模式。

固定策略如下：

- avatar 调用直接失败
- 记录清晰的错误日志，至少说明失败发生在 avatar 请求阶段，且与 `system` 消息兼容性或请求校验有关
- 不修改既有的 takeover 主循环语义：本轮不回写 prompt，等待下一轮轮询

这样做的原因是：一旦静默降级到没有 `system` 的模式，就会重新暴露分身角色漂移问题，破坏本次改动的产品目标。

## Prompt 工件范围控制

固定 `system` prompt 是 takeover 模块内部的一部分协议工件，不是一个开放式策略收纳箱。为了防止未来不断向其中堆叠无关规则，本期增加以下范围约束：

- prompt 必须保存在 takeover 模块拥有的固定常量中
- prompt 的职责只限于定义分身身份、边界和默认协作方式
- 后续对 prompt 的修改应同步更新相关测试，确保行为变化是显式的
- 与当前“管理者分身”目标无关的产品策略，不应顺手塞入这条 prompt

## 最小改动范围

本次实现建议尽量控制在以下范围：

- `packages/opencode-takeover/src/avatar-client.ts`
- `packages/opencode-takeover/src/types.ts`
- 一个新增的 prompt 常量文件

默认不改或只做最小签名调整的文件：

- `packages/opencode-takeover/src/mirror.ts`
- `packages/opencode-takeover/src/takeover-runner.ts`

## 验证策略

### 单元级验证

至少覆盖以下断言：

- 发往 avatar API 的 `messages[0]` 恒为固定 `system`
- 后续 mirrored messages 的数量、顺序和内容保持不变
- 现有 `user / assistant` 镜像逻辑不受影响
- 当 provider 因 `system` 角色或请求校验拒绝请求时，avatar 调用失败且不会静默移除 `system`

### 行为级验证

在真实或模拟对话中，重点观察分身是否稳定体现以下行为：

- 把自己定位为管理者 / 决策者
- 优先委派执行者去读文件、调查或实现
- 遇到越界请求时，先重述目标，再重新派发
- 默认输出偏任务拆解、验收口径和回报要求，而不是实现细节

为降低主观解释空间，至少覆盖以下对抗场景：

1. **执行者要求分身亲自读代码**
   - 输入特征：执行者让分身自己去看文件或调查实现
   - 通过标准：分身明确保持边界，并把调查任务派回执行者

2. **执行者要求分身直接给实现细节或代码**
   - 输入特征：执行者请求分身直接写代码、给补丁或给命令
   - 通过标准：分身转为给出目标、约束、验收口径或方案判断，而不是产出代码

3. **正常规划请求**
   - 输入特征：执行者请求下一步方向或任务拆解
   - 通过标准：分身以“目标 / 委派 / 验收 / 回报”风格中的一种中等结构化方式回应，而不是泛泛聊天

## 风险与兼容性

### 1. 目标 chat completion 实现是否接受 `system`

当前 `avatar-client.ts` 是按标准 `messages` 数组直发 `/chat/completions`。从接口形态看，支持 `system` 角色的概率较高，但仍应通过测试确认目标分身 API 没有额外限制。

### 2. 提示词过硬可能让分身显得机械

如果 prompt 过度强调禁止项，分身可能变成只会拒绝的调度器。为避免这一点，本设计明确采用“角色优先 + 中等结构化”的写法，让限制规则服务于管理者人设，而不是反客为主。

### 3. 提示词过软可能无法稳定纠偏

如果身份和边界描述太弱，分身仍可能偶发性地亲自讨论实现细节或越界调查。因此最终文案需要在“管理者语气自然”与“边界足够硬”之间取得平衡。

## 验收标准

本设计实现后，至少满足以下标准：

1. `@remi/opencode-takeover` 发往分身模型的请求中，第一条消息固定为内置 `system` prompt
2. 该 prompt 是固定字符串，不依赖运行时动态拼接
3. 现有消息镜像和 takeover 主循环行为保持兼容
4. 分身在实际对话中稳定表现为管理者 / 决策者，而不是亲自执行工程任务

## 后续演进方向

如果这次固定 `system` prompt 效果稳定，下一步可以考虑：

1. 继续迭代管理者 prompt 文案，提高委派质量和验收表达
2. 为分身与执行者之间引入更稳定的回报格式约定
3. 结合后续 verdict 协议，把“继续调查 / 开始实现 / 暂停等待 / 请求澄清”进一步结构化
