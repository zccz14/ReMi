# 分享页个人名片化设计

## 背景

当前 `/share` 页面仍是一个偏工具型的分享页：顶部标题与一句说明，下方直接展示二维码、链接与复制按钮。它能完成“把公开资料链接分享出去”的基本动作，但缺少身份感与邀请感。

对于 ReMi 这类带有“分身”属性的产品，分享页不仅是一个跳转入口，也应该承担“先让对方感受到我是谁”的作用。相比单纯展示二维码，一个更像个人名片的分享页更容易降低陌生感，也更贴近用户的分享心智。

本次改动目标是在不改变分享链接结构的前提下，把分享页从“二维码工具页”提升为“个人名片型分享页”。

## 目标

- 保留现有分享能力与链接结构，继续分享 `/profile/:pubKey`
- 让分享页优先展示“人”，而不是优先展示“二维码”
- 强化 ReMi 的个人连接感，用更贴近邀请的文案替换当前说明文案
- 支持二维码中心图：有用户头像时优先用头像，无头像时回退 App Logo
- 保持加载、失败、成功三态明确且行为安全

## 非目标

- 不改动公开资料页 `/profile/:pubKey` 的路由、数据协议或展示结构
- 不新增复杂分享渠道集成（如系统分享面板、社交平台 SDK）
- 不在本期引入海报生成、多尺寸导出或下载到相册等扩展能力
- 不新增字段级隐私控制或额外公开资料字段

## 方案对比

### 方案 A：邀请卡优先

以品牌文案和氛围为主，头像与二维码退居次级位置。优点是更像产品邀请页，品牌感强；缺点是用户个人身份不够突出，不符合“主要是个人名片”的目标。

### 方案 B：个人名片优先（采用）

顶部先展示头像、昵称与简介，主文案强调“链接我”，二维码作为名片下半部分的核心动作。优点是更像个人名片，身份识别更强，和用户分享心智一致；缺点是品牌露出相对克制，需要通过次级元素维持 ReMi 识别度。

### 方案 C：品牌与名片均衡

把身份信息和二维码拆成两个并列层级，同时保留较强的产品感。优点是结构平衡；缺点是第一眼注意力更分散，不如方案 B 那么明确地以“个人”为中心。

综合权衡后采用方案 B，并保留一个轻量的 ReMi 品牌锚点，例如页面标题、App Logo 回退图或名片上的产品标识。

## 页面结构

页面继续复用 `packages/web/src/pages/SharePage.tsx`，不新增新路由。

建议结构如下：

1. 页面标题区：保留“分享分身”或同类页面级标题，用于导航语义
2. 个人名片区：
   - 头像
   - 公开昵称
   - 个人简介（有内容时展示）
   - 主文案 `来 ReMi 链接我`
   - 副文案，用较轻语气说明可以先认识分身再开始聊天
3. 二维码区：
   - 展示分享链接对应二维码
   - 中心图优先用用户头像，无头像时回退 App Logo
4. 操作区：
   - 复制链接
5. 链接文本区：继续展示完整分享链接，便于复制与确认

整体上，页面的信息顺序应从“我是谁”过渡到“如何联系我”，而不是一上来展示二维码。

## 数据契约与兜底规则

分享页继续复用现有 owner profile bootstrap 请求，并直接从响应数据读取当前公开资料字段：

- `displayName`
- `bio`
- `hasAvatar`
- `avatarVersion`

这些字段的语义和现有 `packages/web/src/lib/profile.ts` 保持一致。

### 展示兜底

- `displayName` 为空时，复用现有 `getFallbackDisplayName(pubKey, displayName)` 规则，展示截断后的公钥，而不是新引入 `未设置昵称` 文案
- `bio` 为空时直接隐藏简介区域，不保留空白占位
- `hasAvatar === false` 或 `avatarVersion === null` 时，主名片头像与二维码中心图都视为“无头像”路径
- 若 `publicKey` 本身不可用，则分享页保持动作禁用，并仅展示错误态，不尝试拼接分享链接

## 数据与状态

现有分享页在进入后会先请求 owner profile bootstrap，确认公开资料可用后再展示二维码。本次继续沿用这个启动逻辑，不改变请求入口。

### ready

- 展示完整名片内容
- 展示二维码与链接
- 启用复制链接按钮

### loading

- 展示名片骨架或占位结构，而不是只展示一行提示
- 保留 `正在准备公开资料…` 文案
- 不展示真实二维码与链接
- 所有分享动作保持禁用

### error

- 展示 `公开资料准备失败，请稍后重试。`
- 不展示二维码与可复制链接
- 复制/保存类动作保持禁用
- 页面主体仍保留名片容器，避免布局突然塌陷

## 二维码中心图设计

二维码继续基于现有 `qrcode.react` 渲染，不改变二维码承载的数据内容。

### 中心图优先级

1. 用户头像可用时，中心图使用用户头像
2. 用户头像不可用时，中心图使用 App Logo
3. 若中心图资源异常或无法安全渲染，回退到无中心图的纯二维码

### 资源来源

- 头像 URL 直接复用现有 `buildAvatarUrl(publicKey, avatarVersion)` 逻辑
- App Logo 固定使用现有静态图标资源 `packages/web/public/icons/icon-192.png`
- 主名片头像区域与二维码中心图共用相同的头像可用性判断，但分别维护图片加载失败回退，避免一个区域失败后影响另一个区域

### 渲染方式

优先使用 `QRCodeSVG` 支持的内建中心图能力；若当前版本无法稳定支持，则本期直接回退到纯二维码，不使用 overlay 方案。这样可以收敛实现复杂度，也避免做出跨浏览器不稳定的二维码叠图。

本期二维码硬约束：

- 纠错等级固定为 `H`
- 中心图宽高不超过二维码边长的 20%
- 中心图保留足够留白，避免压到定位块
- 若头像中心图加载失败，回退到 App Logo 中心图
- 若 App Logo 中心图也不可用，则回退纯二维码

### 可扫性要求

- 二维码尺寸保持当前量级或略增，不做过度缩小
- 纠错等级固定为 `H`
- 不在二维码四周叠加装饰性遮挡元素

## 文案

建议中文文案结构如下：

- 页面标题：`分享分身`

- 副文案：`先认识我的分身，再开始聊天`

## 测试策略

本次测试重点不在二维码算法本身，而在页面状态与渲染决策：

- 请求成功时，页面显示个人名片信息与二维码
- 请求中时，页面展示占位态且动作禁用
- 请求失败时，页面展示错误态且动作禁用
- 有头像时走头像中心图路径
- 无头像时走 App Logo 回退路径
- 头像与 Logo 都失败时走纯二维码路径
- 文案更新后，测试不要继续绑定旧文案

单测应优先通过稳定标记验证渲染决策，而不是依赖二维码 SVG 内部结构；E2E 只验证主文案、二维码存在和链接存在的回归，不承担中心图分支细节。

## 风险与缓解

### 风险 1：二维码中心图影响扫码

缓解：优先使用库内建中心图能力；控制中心图尺寸；提高纠错级别；必要时回退纯二维码。

### 风险 2：头像资源加载失败导致视觉破碎

缓解：为头像与二维码中心图分别设置明确回退路径，避免资源失败时整个分享区不可用。

### 风险 3：分享页过度品牌化，削弱“个人名片”定位

缓解：把头像、昵称、bio 放在视觉最前面，品牌只做辅助锚点，不与人物身份争主位。

## 验收标准

- `/share` 页面在视觉上首先呈现用户个人名片，而不是单独的二维码工具块
- 主文案使用 `来 ReMi 链接我`
- 页面成功态可展示带中心图的二维码，且中心图遵循“头像优先，Logo 回退”规则
- 当头像与 Logo 资源都不可用时，页面仍能回退为纯二维码且不影响复制链接
- loading / error / ready 三态行为正确，分享动作不会在未准备好时误触发
- 中英文文案与测试同步更新，无现有回归失败
