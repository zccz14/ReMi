# Cloudflared Local Deployment

## Summary

Deploy ReMi from a local machine using a single public URL exposed by `cloudflared`, with the Hono server as the only local entrypoint. In development mode, Hono serves `/api/*` itself and proxies frontend traffic to the Vite dev server. This keeps the external shape of the app simple: one URL, one local port, no split frontend/backend domains.

## Motivation

The immediate goal is not long-term production hosting. It is to let other people open and play with the app quickly while development continues on the local machine. The deployment setup should therefore optimize for:

- fast setup on the existing Mac
- one shareable public URL
- no CORS or multi-origin complexity
- a clean upgrade path from temporary demo access to later custom-domain hosting

## Goals

- Expose the whole app through one public URL created by `cloudflared`
- Keep the app behind one local port owned by Hono
- Preserve existing API routes under `/api/*`
- Allow the frontend to run in Vite dev mode during the first deployment stage
- Make the later transition to custom domain or static serving require minimal code changes

## Non-Goals

- Full production hardening for 24/7 availability
- Automated cloud deployment or infrastructure provisioning
- Domain binding for `remi.zccz14.com` in the first stage
- Replacing Vite with a different frontend toolchain
- Perfect remote HMR behavior for external visitors over `cloudflared`

## Phase Boundaries

This work is intentionally split into two phases.

### Phase 1: Temporary public demo

In scope for this spec:

- Hono as the single local entrypoint
- `WEB_MODE=proxy`
- Vite dev server behind Hono
- temporary `trycloudflare.com` public URL
- documentation and commands needed to share the app quickly

Out of scope for implementation in this phase:

- custom hostname binding
- always-on process management
- full static serving rollout

### Phase 2: Hardening path

Documented now for compatibility, but not required to finish the current task:

- `WEB_MODE=static`
- Vite build output served directly by Hono
- optional custom domain and named tunnel setup

Phase 2 exists so that Phase 1 does not paint the project into a corner, but Phase 1 should be implementable and verifiable on its own.

## Proposed Approach

Use Hono as the only local server exposed to the outside world.

### Local Ports

| Service         | Port   | Responsibility                                           |
| --------------- | ------ | -------------------------------------------------------- |
| Hono server     | `8787` | Public local entrypoint, API handling, frontend dispatch |
| Vite dev server | `5173` | Frontend pages, assets, HMR in dev mode                  |

### External Request Flow

```text
Browser
  -> cloudflared temporary URL
  -> http://localhost:8787
  -> Hono
     - /api/* handled directly by server routes
     - all frontend requests proxied to Vite dev server
```

The external user only sees one HTTPS URL. The app only exposes one local port to `cloudflared`.

## Current Mode

Frontend delivery for this task uses one explicit mode: `WEB_MODE=proxy`.

- Hono handles `/api/*`
- Hono proxies page and asset requests to Vite
- `cloudflared` points to `http://localhost:8787`
- the public URL is the temporary `*.trycloudflare.com` URL generated by `cloudflared`

This task implements, tests, and documents proxy mode only.

Future compatibility note: a later task may add a static-serving mode behind the same one-public-URL and one-local-port shape, but that mode is not implemented, verified, or accepted here.

## Server Routing Design

The Hono server becomes the boundary between public traffic and local app internals.

### API Routing

- Existing `/api/*` endpoints keep their current behavior
- API requests must never be swallowed by frontend proxy logic
- API clients continue using relative paths like `/api/...`

### Frontend Routing in Proxy Mode

After API routes are registered, Hono handles the remaining requests as frontend traffic.

This includes:

- HTML document requests
- Vite asset paths such as `/src/*`
- Vite internal paths such as `/@vite/*`
- static assets and module requests
- websocket or HMR-related upgrade traffic if supported by the chosen proxy implementation

The purpose is that a browser visiting the public URL can load the whole Vite app without needing to know the Vite port.

### HMR Expectation

Remote HMR through the `cloudflared -> Hono -> Vite` chain is explicitly not a success criterion for Phase 1.

- local development on the Mac should still use normal Vite behavior
- remote visitors only need page usability, routing, and API functionality
- if remote HMR works, it is a bonus, not a requirement
- if websocket proxying proves unreliable, the fallback is to preserve functional page loads and accept manual refresh for remote sessions

## Cloudflared Usage

Stage one uses a temporary Cloudflare URL instead of a custom domain.

### Initial Command Shape

```bash
cloudflared tunnel --url http://localhost:8787
```

This produces a temporary public URL under `trycloudflare.com`.

### Why Temporary URL First

- no DNS setup is required
- no domain ownership configuration is needed yet
- app code stays identical when later moving to a named tunnel or custom hostname
- it validates the real requirement first: outsiders can open the app and use it

## Security and Exposure Assumptions

This setup exposes a development machine to the public internet through a temporary URL, so the boundary assumptions must be explicit.

- only the Hono entrypoint on `localhost:8787` is exposed through `cloudflared`
- Vite must bind explicitly to `localhost` and must not be exposed directly
- all public traffic must pass through Hono's route boundary first
- no extra admin, debug, or internal-only routes should be newly exposed on the shared public Hono port
- existing authentication and authorization rules for protected API routes remain in force
- this phase assumes demo-grade trust posture, not production hardening

This means the deployment task is acceptable for controlled sharing and testing, but not yet for sensitive or high-availability usage.

## Developer Workflow

The first version of the workflow should separate app startup from tunnel startup.

### App Startup

Provide one local command for the app itself, for example a `dev:public` style command that starts:

- Hono in proxy mode on `8787`
- Vite on `5173`

### Tunnel Startup

Run `cloudflared` separately from npm scripts in the first version.

Reasoning:

- `cloudflared` depends on machine-level installation and login state
- tunnel credentials and process lifecycle are deployment concerns, not normal app dev concerns
- keeping it separate makes local debugging simpler

Documentation should still provide the exact tunnel command and expected behavior.

## Rollback Plan

If the unified-entrypoint setup causes problems, rollback should be immediate and low-risk.

### Code rollback

- disable frontend dispatch by switching back to the previous server startup path
- keep the existing API server behavior intact
- remove or ignore `WEB_MODE=proxy`

### Operational rollback

- stop the `cloudflared` process
- stop the Hono proxy-mode process if needed
- continue local development using the pre-existing local URLs directly

Rollback success means the app is no longer publicly reachable, but local development and API behavior still work as before.

## Configuration Changes

Minimal configuration changes are preferred.

### Frontend

- Prefer relative API paths so requests naturally target the current origin
- Avoid introducing a separate frontend env var for public API base URL in this stage

### Server

- Add a clear env switch for frontend serving mode, such as `WEB_MODE`
- Add Vite target location config if needed, but keep defaults local and explicit

## Risks and Mitigations

### Local Machine Availability

Risk:

- the app disappears when the Mac sleeps, disconnects, or stops running the processes

Mitigation:

- accept this for the temporary demo phase
- document that the machine must stay awake and online while sharing the URL

### HMR Through Tunnel

Risk:

- Vite HMR websocket traffic may be less reliable through the proxy+tunnel chain

Mitigation:

- optimize for external usability, not perfect remote HMR
- if needed, accept that remote visitors get page reload behavior while local development remains normal

### Proxy Boundary Bugs

Risk:

- the frontend proxy may accidentally intercept API routes or fail on streamed responses

Mitigation:

- keep API routing explicit and earlier than frontend dispatch
- add focused tests for route separation and frontend fallback behavior

## Verification Plan

### Automated

- keep the existing test suite green
- add targeted tests covering:
  - `/api/*` remains owned by the server
  - non-API requests enter frontend dispatch
  - this phase does not implement or verify static asset serving by Hono

### Manual

1. Start Vite and Hono locally
2. Open `http://localhost:8787` and confirm the app loads
3. Verify API requests succeed through the same origin
4. Start `cloudflared tunnel --url http://localhost:8787`
5. Open the generated public URL from another browser or device
6. Verify page load, route refresh, and core chat flow
7. Verify no unexpected internal or debug-only routes are publicly reachable through the shared Hono port

## Implementation Outline

1. Add server-side frontend dispatch with `WEB_MODE`
2. Implement Vite proxy behavior for dev mode
3. Add a unified app startup command for public local dev
4. Document `cloudflared` temporary URL workflow in the repo
5. Add focused verification for route ownership and SPA behavior

## Success Criteria

- A single `cloudflared` temporary URL opens the full app for external users
- The temporary URL maps to one Hono local port only
- Frontend and API both work under the same origin
- No extra public frontend/backend domains are required
- The code structure remains ready for later migration to custom domain and static serving
- This phase does not implement or verify static asset serving by Hono
