# 访谈锚点提取的高召回优先设计

## 概述

当前访谈流程里的锚点提取过于偏向“高层认知总结”，导致用户已经明确说出的事实信息没有稳定沉淀为灵魂锚点。现阶段项目的主要问题不是锚点过多，而是锚点过少，因此提取策略应从“少而精”切换为“先多写多记，后续再归并”。

本设计聚焦访谈流程中的锚点提取阶段，目标是在不改动现有锚点存储 schema 的前提下，提高明确事实与中低层信息的召回率，同时保留认知类锚点的持续提取能力。

## 背景问题

当前 `packages/server/src/interview/prompts.ts` 中的 extraction prompt 有两个偏置：

- 强调 `question` 应是“通用的、可复用的认知问题”
- 强调“不要重复提取已有锚点中已覆盖的内容”

这会把模型推向抽象总结与强去重，造成两个结果：

- 明确事实被压缩成少量高层解释，很多本应沉淀的事实未入库
- 不同粒度、不同视角但都有效的信息被过早视为“已覆盖”

项目当前阶段需要的是尽量保留信息，而不是过早归纳信息。

## 目标

- 提高访谈中“明确事实”类信息的提取率
- 允许同一条用户消息产出多个锚点
- 允许事实锚点与认知锚点并存
- 将去重策略从“语义接近即跳过”收缩到“明显等价才跳过”
- 保持现有 `<anchor><question><answer>` 输出协议不变
- 保持现有锚点表 schema 不变

## 非目标

- 本轮不引入新的锚点字段，如 `type`、`confidence`、`source_span`
- 本轮不做历史锚点归并或抽象化重写
- 本轮不改变 recall runtime、矛盾检测协议或 interview 外部 API
- 本轮不解决“锚点过多后如何聚合”问题

## 核心产品判断

现阶段锚点提取应遵循以下产品判断：

- 锚点过少比锚点过多更危险
- 明确说出的事实默认都值得记录
- 抽象总结不是提取阶段的首要目标
- 合并、归纳、上卷应该发生在后续阶段，而不是首次提取阶段

因此，本轮的优化方向是 **高召回优先**，具体执行原则为：宁可多记，后续再归并；不要因为追求抽象、优雅、低重复而漏掉明确事实。

## 提取原则

### 1. 事实优先

每条用户消息都应先被视为“可沉淀的记忆”，而不是“待压缩的认知摘要”。

提取时应按如下顺序扫描：

1. 身份 / 人物事实
2. 当前在做的事
3. 计划 / 目标
4. 事件 / 经历 / 触发点
5. 判断 / 偏好 / 原则

只要用户消息中存在新的明确事实，就应优先产出事实锚点。

### 2. 允许一条消息产出多个锚点

单条用户消息中可能包含多个独立信息单元。提取器不应为了“精炼”而只保留一个代表性锚点。

如果一条消息同时表达了多个事实，允许产出多个锚点，只要它们分别锚定了不同信息。

### 3. 事实锚点与认知锚点并存

同一句话里既可能有事实，也可能有更高层的认知。两者不冲突，不应二选一。

提取策略应先尽量保住事实，再补充认知类锚点，而不是让认知总结覆盖事实本身。

### 4. 只拦明显重复

去重只应用于明显等价的重复内容。以下情况不应视为重复：

- 信息粒度不同
- 视角不同但都提供新增信息
- 对已有事实的补充说明
- 状态更新或时间推进后的新事实

也就是说，“相关”不等于“重复”，“可归并”也不等于“应在提取时丢弃”。

### 5. 保持问题表述稳定

虽然本轮放宽了 `question` 的形态，但仍要求其问法保持稳定，以避免同一事实因问法漂移而被重复记录。

最小约束如下：

- 默认使用第一人称视角进行锚定
- 凡是锚定本体的人格、认知、偏好、经历与事实，`question` 中的主语必须使用“我”，不得使用“用户”
- 优先使用一般现在时或稳定状态表达，不把短期时间词直接写入 `question`
- 时间、条件、补充背景优先进入 `answer`，而不是进入 `question`
- `question` 应锚定一个稳定信息槽位，而不是一次性上下文表述

正向示例：

- `我最近在忙什么？`
- `我现在在做什么项目？`
- `我的决策方式是什么样的？`

反向示例：

- `我在上周二下午具体忙了什么？`
- `当时为什么突然去做那个决定？`
- `刚才提到的那件事到底是怎么发生的？`

这些反向示例不是不能提取，而是不适合作为稳定的 `question` 形态；若信息值得记录，应改写为更稳定的锚定问题。

## 锚点形态

本轮不修改锚点 schema，继续沿用：

```xml
<anchor>
  <question>...</question>
  <answer>...</answer>
</anchor>
```

但调整 `question` 的语义边界：

- `question` 不再要求必须是高层认知母题
- `question` 可以是自然的事实锚定问题
- `question` 的职责是稳定锚住信息，而不是强行把信息抽象成哲学层命题

允许的 question 形态包括：

- 身份型问题
- 当前状态型问题
- 正在进行的事项型问题
- 目标与计划型问题
- 事件触发型问题
- 决策模式或偏好型问题

## Prompt 调整方案

### 当前问题规则

当前 extraction prompt 中最需要调整的是两条规则：

- “question 应该是通用的、可复用的认知问题”
- “不要重复提取已有锚点中已覆盖的内容”

### 调整后的规则方向

建议将 extraction prompt 改为强调以下规则：

1. 每个锚点包含 `question` 与 `answer`
2. `question` 应该是能稳定锚定该信息的自然问题，可以是事实问题，也可以是认知问题
3. 当前阶段以召回率优先，宁可多记，后续再归并，不要因为追求抽象和精炼而漏掉明确事实
4. 优先提取用户明确说出的身份、事项、目标、事件、经历、关系、地点、时间线与动机
5. 如果一条消息中有多个独立信息点，应尽量分别提取
6. 只有当某条信息与已有锚点明显等价时才跳过
7. 如果没有任何新增信息，才输出空结果
8. `question` 的表述应尽量稳定，避免同一事实每次都换一种问法
9. 涉及本体的人格认知、偏好、经历与事实时，`question` 必须使用“我”作为主语，不得使用“用户”，以避免和第三方访问者混淆

### Few-shot 与示例约束

如果 prompt 中需要示例或正反例，必须满足以下要求：

- 使用完全脱敏、虚构、不可回溯到真实用户的数据
- 不使用真实用户数据库中的原话、身份、地点、项目或关系信息
- 示例只用于说明规则，不携带任何真实用户内容

## 抽取优先级

对单条用户消息，提取器应采用如下优先级：

1. 先穷尽明确事实
2. 再提取明显的目标、动机、计划
3. 最后补充高层认知、原则、偏好

这意味着在信息密度较高的消息里，如果模型无法完整输出所有候选锚点，应优先保留事实类锚点，再补认知类锚点。本轮不引入独立配额机制，也不新增排序或裁剪后处理逻辑；该优先级仅通过 prompt 行为约束实现。

## 单消息产出边界

本轮目标是提高召回率，但不把 extraction 模块扩展成“无限展开”的信息拆分器。

边界如下：

- 不新增显式的程序化上限裁剪逻辑
- 默认由模型按“独立且值得记录”的原则自然裁剪
- 一条消息只要仍在表达同一事实的改写、重复、语气补充，不应机械拆成多个锚点
- 一条消息若同时包含多个明确事实、目标、经历或判断，则允许提取多个锚点

也就是说，本轮追求的是“不要漏掉独立信息单元”，而不是“尽可能把一句话切成最多碎片”。

## 去重边界

为避免“过度去重导致漏提取”，本轮采用更保守的去重边界：

- 完全同义、信息等价：可跳过
- 同主题但信息粒度不同：保留
- 同一时期不同事项：保留
- 对已有锚点增加条件、原因、背景：保留
- 新状态覆盖旧状态：允许保留，后续再由归并层处理

提取层的职责是保住信息，不是裁决最终知识图谱该如何压缩。

## 与矛盾检测的兼容边界

本轮虽然不改动 contradiction 协议与主流程，但必须保持以下兼容性要求：

- 状态演进、时间推进、背景补充产生的新锚点，不应被当前 contradiction 流程大面积误判为“真正矛盾”
- “过去如此、现在变化了”与“条件不同导致行为不同”应继续被视为可并存信息，而非自动冲突

这意味着测试中需要至少覆盖一组“状态更新但非矛盾”的样例，确保召回率提升不会明显破坏当前访谈体验。

## 实现边界

本轮默认只改动锚点提取相关模块：

- `packages/server/src/interview/prompts.ts`
- 如有必要，调整 `packages/server/src/interview/extractor.ts` 的后处理校验

原则上不改：

- DB schema
- route 层协议
- SSE 协议
- recall 与 contradiction 主流程

## 测试策略

本轮遵循 TDD，先写失败测试，再改生产代码。

至少应覆盖以下场景：

1. 单条消息包含多个明确事实时，允许提取多个事实锚点
2. 同条消息同时包含事实与认知时，两类锚点可并存
3. 与已有锚点主题接近但粒度不同的信息，不应被误判为重复
4. 当消息确实没有新增信息时，仍允许返回空数组
5. prompt 中示例若存在，应为脱敏虚构内容
6. 典型认知类输入在新规则下，仍能提取出认知锚点，而不是被事实扫描完全吞掉
7. 状态更新类新锚点不会明显放大 contradiction 误报

测试重点应放在“明确事实不再大面积漏提取”的行为约束，而不是要求模型输出唯一标准答案。

### 最小验收样例

为避免验收标准只停留在抽象规则，本轮至少应使用以下脱敏样例做 fixture 级验证：

1. 多事实输入
   - 输入：`我最近一边准备考试，一边在做一个小工具，也在投简历。`
   - 期望：至少提取出“最近在忙什么”与“正在做什么项目 / 事项”两类事实锚点
   - 期望：不能只压缩成单一的高层总结锚点

2. 事实 + 认知并存输入
   - 输入：`我现在在做独立开发，因为我不喜欢太重的团队协作流程。`
   - 期望：至少保留一个事实锚点（正在做独立开发）
   - 期望：同时允许保留一个认知锚点（对协作方式的偏好 / 判断）

3. 粒度不同但不应去重
   - 已有锚点：`我最近在忙什么？ -> 在找工作`
   - 输入：`我最近主要在投后端岗位，也在准备系统设计面试。`
   - 期望：新增信息不应被整体视为“已覆盖”

4. 无新增信息输入
   - 已有锚点已明确覆盖某事实
   - 输入仅重复同一事实且无新增条件、状态或背景
   - 期望：允许返回空数组

5. `question` 稳定性输入
   - 输入：`上周二下午我去面试了一家创业公司，现在还在等结果。`
   - 期望：若提取相关锚点，`question` 应锚定为稳定槽位，例如“我最近在经历什么求职进展？”之类的稳定问法
   - 期望：`question` 不应直接包含“上周二下午”“刚才”“当时”等短期上下文词

6. 本体指代输入
   - 输入：`我做决定时更看重长期空间，不太在意短期波动。`
   - 期望：若提取认知锚点，`question` 应使用“我”作为主语，例如“我的决策偏好是什么样的？”
   - 期望：`question` 不应写成“用户的决策偏好是什么样的？”之类存在歧义的表述

## 验收标准

- extraction prompt 的主规则从“抽象复用优先”切换为“高召回优先”
- `question` 允许表达事实型锚定问题
- `question` 需满足最小稳定性约束：默认第一人称、避免把短期时间词直接写入问题、优先锚定稳定信息槽位
- 涉及本体的人格认知与事实时，`question` 主语统一使用“我”，不使用“用户”
- 单条消息可稳定提取多个锚点
- 去重策略明确收缩到“明显等价才跳过”
- 示例约束明确要求脱敏、虚构、不可回溯
- 新增测试覆盖事实优先、保守去重边界、认知提取不回归、状态演进不误判矛盾
- 最小验收样例可通过 fixture 级测试验证
- fixture 级测试可验证 `question` 不直接携带短期上下文词，避免问法漂移
- fixture 级测试可验证本体相关 `question` 统一使用“我”而非“用户”

## 风险与权衡

### 风险 1：短期内锚点数量上升更快

这是预期结果，不是失败。当前阶段的产品目标本就是提高留存信息量。

### 风险 2：锚点重复度上升

这也是可接受代价。重复治理属于后续归并层问题，不应反向压制当前提取召回率。

### 风险 3：question 形态更不统一

短期可以接受。相比统一命名风格，当前更重要的是先沉淀信息。未来如需规范化，可在归并或重写阶段处理。

## 后续工作

如果本轮上线后锚点数量明显提升，下一阶段可继续讨论：

- 是否引入锚点类型字段（事实 / 认知 / 事件 / 状态）
- 是否增加 source span 或 message linkage 以支持更稳定的归并
- 是否在 recall 或 profile 层做抽象化聚合

但这些都不属于本轮范围。
