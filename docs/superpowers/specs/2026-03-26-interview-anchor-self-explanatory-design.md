# 访谈灵魂锚点的自解释提取设计

## 概述

当前访谈锚点提取已经从“高层认知总结优先”切到“高召回优先”，但锚点本体仍然过薄。仅有 `question + answer` 的结构虽然能保住信息，却经常无法自解释：锚点在谈哪个概念域、什么条件下成立、项目名或术语具体指什么，往往要依赖上下文或长 answer 才能补全。

本设计在 **不修改锚点 schema** 的前提下，进一步调整访谈提取策略：让锚点从“高召回答案片段”升级为“可按需召回的最小自解释问答单元”。核心方向不是把 answer 写得更长，而是让 question 更明确、锚点更多、边界更清晰，并在必要时额外沉淀术语定义锚点。

## 背景问题

当前 `packages/server/src/interview/prompts.ts` 中的 extraction prompt 虽然已经强调事实优先和宁可多记，但仍然缺少以下约束：

- 没有明确要求 question 携带语境范围、成立条件与概念边界
- 没有明确要求项目名、缩写、内部术语在 question 中补足语义
- 没有抑制“把多个场景和前提塞进一个跨边界 answer”的倾向
- 没有把“术语定义本身”视为可独立召回的锚点类型

因此会出现两类典型问题：

- 锚点能保存信息，但离开当前对话后不够自解释，召回时仍需要模型二次猜测
- answer 变长、信息堆叠，而 question 过宽，导致 recall 粒度仍然过粗

## 目标

- 让提取出的锚点在仅看 `question` 时就大致知道它在谈什么
- 让 `question` 显式表达概念范围、适用条件、讨论对象或术语语义
- 控制 `answer` 不要变成包罗各种情况的长段落
- 允许把一条用户消息拆成更多边界清晰的 question，以支持按需 recall
- 当用户提到项目名、方法论、专有概念、缩写时，允许额外沉淀术语定义锚点
- 保持现有 `<anchor><question><answer>` 输出协议不变
- 保持现有数据库 schema 与外部 API 不变

## 非目标

- 本轮不新增 `scope`、`applicability`、`type`、`confidence` 等结构化字段
- 本轮不引入术语表、知识图谱或显式链接表
- 本轮不改变 recall runtime、向量检索协议或路由协议
- 本轮不要求 answer 完整覆盖所有例外情况与边界情况
- 本轮不解决“多个细粒度锚点如何在更高层聚合展示”问题

## 核心产品判断

本轮的判断有四条：

- 比起“一个宽泛问题配一个长 answer”，更应该要“多个边界清晰的问题配较短 answer”
- 锚点的主要召回单位是 `question`，因此自解释能力应优先放在 question，而不是押注 answer
- 对于项目名、术语、缩写这类容易失真的对象，仅保留裸名词不够，必须把语义对象补足
- 当术语在当前消息里出现了可独立提取的定义性表达时，应允许额外沉淀术语定义锚点，而不是只把定义塞进主锚点 answer

换句话说，本轮提取策略从“高召回优先”升级为：

> **高召回 + 自解释 + 术语显化 + 细粒度 recall 优先**

并且本轮所有判断都应遵循一个实现约束：

> **只基于当前消息文本中的可见证据做提取判断，不依赖会话历史、外部知识库、产品配置、隐式词表或模型先验补全。**

## 设计原则

### 1. Question 是主要的语义承载体

在不改 schema 的前提下，question 不再只是一个抽象槽位名，而要承担更强的边界表达职责。

每条 question 应优先补足以下信息中的关键部分：

- **语境范围**：在谈工作协作、独立开发、亲密关系、长期规划、项目设计还是其他领域
- **成立条件**：在高压力下、时间紧时、资源不足时、面对陌生人时、信息不完整时等
- **概念槽位**：偏好、原则、判断标准、行为模式、当前状态、术语定义等
- **术语语义**：出现项目名、方法名、代号、缩写时，要说明该术语在这里指什么对象

这不是要求机械拼接四段说明，而是要求 question 在最小可读长度内，把边界说清。

### 2. Answer 保持短而聚焦

answer 的职责仍是承载用户的具体表述，但不应再默认承担所有边界说明。

本轮应显式压制以下情况：

- 把多个场景、多个前提、多个概念对象都堆进一个长 answer
- 用 answer 补 question 没说清的语义对象
- 用长 answer 代替多个更细粒度的锚点

如果一句用户消息里确实包含多个场景、多个条件或多个术语对象，应优先拆成多条锚点，而不是试图写出一个“包罗万象”的 answer。

### 3. 细粒度 question 优先于大而全总结

当前阶段 recall 的核心诉求不是减少锚点数量，而是提高“按需召回”的精度。

因此提取器应优先产出：

- 更窄的问题
- 更明确的适用边界
- 更容易单独召回的概念单元

而不是优先追求：

- 一个问题概括很多情况
- 一个 answer 覆盖各种例外
- 一个术语顺带解释很多上下文

### 4. 术语显化是提取目标的一部分

当用户提到项目名、产品名、内部黑话、方法论名、缩写或专有概念时，提取器不应把它们当作 answer 里的普通名词略过。

至少要满足其中一条：

- 在主锚点的 question 中补足该术语指的是什么语义对象
- 如果当前消息里出现了该术语的定义句式、解释性同位语或释义短语，再额外生成一条术语定义锚点

这意味着“术语定义”不再只是附带信息，而是必要时可独立沉淀的知识单元。

### 5. 冲突时的优先级

当以下目标发生冲突时，优先级应明确为：

1. 先保证 **question 至少能自解释到足以判别讨论对象**
2. 再保证 **question 仍可被未来同类信息复用**
3. 最后再追求 **表达尽量短**

也就是说，如果“更短”与“更清楚”冲突，允许 question 稍长；但 question 不得机械复述用户原话中的临时上下文指代，应改写为稳定问句。

## Question 写法规则

### 1. 保持稳定可复用

question 仍然必须是稳定问句，不能退化成对当前一句话的机械转写。

可执行约束是：question 不得包含一旦离开当前消息就失义的临时上下文指代，例如：

- `这个`
- `那个`
- `刚才提到的`
- `上周二下午的那个`

不推荐：

- `我刚才说的那个项目为什么重要？`
- `上周二下午我具体怎么想的？`
- `那个方法到底是怎么回事？`

推荐：

- `当我谈到 ReMi 这个 AI 分身项目时，我认为它要解决的核心问题是什么？`
- `当我在高压力的工作协作中做决策时，我更依赖什么判断标准？`
- `我所说的 Ralph-Loop 这种持续主动推进目标的调度方式，核心含义是什么？`

### 2. 优先把范围与条件写进 Question

如果一条判断只在特定领域、特定关系或特定条件下成立，优先在 question 中补足，而不是让 question 保持宽泛，再把所有限制塞进 answer。

例如：

- 相比 `我的决策方式是什么样的？`
- 更优先 `当我在时间紧且信息不完整时做决策时，我更依赖什么判断标准？`

### 3. 术语不能裸奔

当 question 中出现项目名、术语名或缩写时，如果当前消息中给出了定义句式、解释性同位语或释义短语，应尽量把这些消息内证据补进 question，而不是只保留裸术语名。

例如：

- 不推荐 `我为什么喜欢 ReMi？`
- 更推荐 `当我谈到 ReMi 这个 AI 分身项目时，我最看重它的哪一部分？`

- 不推荐 `我怎么看 Ralph-Loop？`
- 更推荐 `当我谈到 Ralph-Loop 这种持续主动调度目标的方式时，我认可它的核心原因是什么？`

### 4. Question 变具体，但不能一次性

允许 question 比当前版本更具体，但必须避免以下两种失控：

- 因为追求自解释，把 question 写成接近整句原话的复读
- 因为追求稳定，又把 question 写回过于抽象的槽位名

目标形态应是：

- 足够具体，能说明“在谈什么、何时成立、对象是谁”
- 又足够稳定，未来仍可作为同类信息的召回入口

### 5. 至少补足一个边界要素

为了让“自解释”变得可执行，给定一条值得提取的锚点，question 至少应显式补足以下边界要素中的一个；若用户原话本身信息密度很高，则可补足多个：

- 语境范围
- 成立条件
- 讨论对象的术语语义

如果 question 三者都没有，只剩抽象槽位名，则不满足本轮目标。

如果 question 中包含项目名、缩写或专有术语，则仅补语境范围或成立条件还不够；还必须满足以下至少一项：

- 在主 question 中直接补足该术语的语义对象
- 按本节后续规则额外生成一条术语定义锚点

## 术语定义锚点

### 1. 触发条件

当用户消息中出现以下对象时，可以按消息内证据规则评估是否额外生成术语定义锚点：

- 项目名、产品名、组织名
- 方法论名、流程名、框架名
- 缩写、代号、内部黑话
- 在当前消息里被当作专有概念讨论的名词

术语定义锚点的判断只基于当前消息文本可见证据；不得依赖会话历史、产品配置、外部知识库或模型“知道这个词”的先验。

### 1.1 强制生成的情况

只要当前消息出现显式定义句式，就必须额外生成术语定义锚点。显式定义句式包括但不限于：

- `X 就是……`
- `我说的 X 指的是……`
- `这里的 X 不是……而是……`

### 1.2 可生成但非必须的情况

如果当前消息中，术语被直接当作讨论对象，且消息内同时给出了可抽取的解释性同位语或释义短语，则可以额外生成术语定义锚点。

例如：

- `ReMi 这个 AI 分身项目……`
- `Ralph-Loop 这种持续主动推进目标的调度方式……`

### 1.3 明确禁止的情况

以下情况不得仅凭模型主观判断去补定义锚点：

- 只是因为某个词看起来不常见
- 只是因为模型“知道”这是某个专有概念
- 当前消息里没有出现定义句式，也没有出现解释性同位语/释义短语

术语定义锚点的三态规则可压缩为：

- **强制**：出现显式定义句式
- **可选**：没有显式定义句式，但出现了解释性同位语或释义短语，且同一条消息中还存在针对该术语对象的独立判断、偏好或用途表达
- **禁止**：既没有显式定义句式，也没有解释性同位语或释义短语

为避免过拆，每个术语在单条消息中最多新增 1 条术语定义锚点。

### 2. 术语定义锚点的职责

术语定义锚点不是百科解释，而是回答：

> 我在这个项目语境里说这个词时，具体指什么？

推荐形态：

- `我所说的 ReMi 这个 AI 分身项目，指的是什么？`
- `我所说的 Ralph-Loop，指的是什么样的主动调度机制？`
- `我所说的灵魂锚点，指的是什么样的知识单元？`

### 3. 与主锚点的分工

- **术语定义锚点**：负责解释“它是什么”
- **主锚点**：负责解释“我怎么判断它、为什么重视它、如何使用它、它解决什么问题”

如果一条用户消息同时包含“术语定义”和“对术语对象的判断”，应优先拆成两条锚点，而不是混在一个 answer 里。

### 4. 不额外生成的情况

以下情况不应额外补术语定义锚点：

- 当前消息里没有出现定义句式、解释性同位语或释义短语
- 当前消息里没有给出可独立提取的定义性表达
- 该词只是普通修饰或泛称使用，没有成为单独的讨论对象

负例示意：

- `我最近在做一个 AI 项目。` 中的“AI 项目”只是普通泛称，且没有定义性表达，不需要额外生成定义锚点
- `我在 ReMi 里也会参考 OpenAI API 的格式。` 若本句重点是实现方式而不是解释 `OpenAI API`，则不必为 `OpenAI API` 单独补定义锚点

## Prompt 调整方向

### 当前规则的不足

现有 extraction prompt 已经有高召回取向，但缺少对“自解释”和“术语显化”的显式约束。

### 调整后的规则方向

建议在 `packages/server/src/interview/prompts.ts` 的 extraction prompt 中增加或强化以下规则：

1. question 不仅要稳定锚定信息，还应尽量补足语境范围、适用条件和讨论对象
2. answer 应保持聚焦，不要把多个条件、多个场景、多个术语解释压成一个长 answer
3. 如果一条消息中包含多个适用边界、多个概念对象或多个术语语义，应按“强制拆 / 不拆 / 可拆”规则处理，而不是合成一个大锚点
4. 当出现项目名、方法论名、缩写、专用术语时，question 不能只保留裸名词，应补足该术语在当前语境中的语义对象
5. 如果当前消息里出现显式定义句式，必须额外生成术语定义锚点；如果只出现解释性同位语或释义短语，则按三态规则决定是否额外生成
6. question 需要自解释，但不得包含脱离当前 question 即失义的上下文指代
7. 只有当当前消息中没有可独立提取的新事实、新定义或新判断时，才输出空结果

## 后处理边界

当前 `packages/server/src/interview/extractor.ts` 已有 `normalizeOwnerQuestion()`，主要处理“用户”到“我”的归一化，以及少量时间表达收缩。

本轮后处理应保持克制：

- 不在代码里硬编码大量领域规则去“程序化生成自解释 question”
- 仍以 prompt 约束为主，让模型产出更好的 question
- 后处理只保留轻量规范化职责，例如第一人称主语、一致的表述收敛

也就是说，本轮不是在 extractor 里引入一套复杂重写器，而是通过 prompt 让生成结果自然更符合目标。

## 与 Recall 的关系

本轮的关键假设是：

- recall 阶段更适合召回多个窄而清晰的问题
- 不适合依赖少量宽问题 + 大段 answer 的二次解析

因此提取策略要主动为 recall 服务：

- 增加 question 数量
- 缩小每条锚点的边界
- 提高单条 question 的可判别性
- 让术语定义在需要时可被直接召回

这样后续推理在面对具体问题时，更容易按需拼装，而不是先召回一个过大的模糊块再让模型切片。

## 多锚点拆分边界

本轮鼓励把一条复杂输入拆成多个更清晰的锚点，但必须增加停止条件，避免为了细粒度而过拆。

拆分应遵循以下边界：

### 1. 强制拆分

以下情况必须拆成多条锚点：

- 同一条消息内同时包含 `术语定义` 与 `对该术语对象的判断 / 偏好 / 用途`
- 同一条消息内包含两个以上条件子句，且每个子句对应不同做法、判断或偏好，例如 `如果……；但如果……`

拆分判断只看当前消息中的独立定义单元与判断单元，不看句号、分号等句法切分形式。

### 2. 不拆分

以下情况不应拆分：

- 只是同一判断的同义补充或修辞重复
- 只是同一对象的背景铺垫，没有形成新的边界要素
- 删除某个子句后主判断不变，只损失修辞或背景补充

### 3. 可拆但非必须

以下情况可以拆，但不是强制：

- 多个围绕同一对象的并列细节，且拆分后 question 会更可判别
- 主锚点已经补足术语语义，但消息内还给出了可以独立召回的简洁释义短语

负例示意：

- `我做技术设计时会先想清楚边界，也会先想测试。` 如果两部分仍共同服务于同一设计方式判断，则不强制拆分
- `ReMi 这个 AI 分身项目我很看重，因为它做认知对齐。` 如果主 question 已经补足 `ReMi` 的语义，且句中没有显式定义句式，则可以不额外拆定义锚点

- 总目标是“不要把多个边界不同的信息压扁”，不是“把一句话切成尽可能多碎片”

## 实现边界

本轮默认只改动锚点提取相关模块：

- `packages/server/src/interview/prompts.ts`
- 如有必要，少量调整 `packages/server/src/interview/extractor.ts`
- `packages/server/test/interview/extractor.test.ts`

原则上不改：

- 数据库 schema
- API route 协议
- SSE 协议
- recall 主流程与向量检索实现
- contradiction 主流程

## 测试策略

本轮继续遵循 TDD，先写失败测试，再改生产代码。

至少应覆盖以下场景：

1. `question` 会把语境范围与成立条件补进去，而不是只给宽泛槽位名
2. 项目名或术语出现在主锚点 question 中时，会补足其语义对象，而不是裸名词
3. 同一条消息中若同时包含术语定义与个人判断，必须拆成术语定义锚点 + 主锚点
4. 如果 answer 同时覆盖多个条件分支或多个术语对象，必须拆分，而不是合成一个跨边界 answer
5. question 不得包含纯上下文指代，例如 `这个`、`那个`、`刚才提到的`
6. 既有的事实优先、高召回、多锚点提取能力不能回退
7. 没有消息内定义性证据的普通泛称或背景术语不会被泛化成多余的定义锚点
8. 当消息只出现陌生缩写、但没有定义句式或解释性短语时，不得凭模型先验补出定义锚点

### 最小验收样例

为避免验收只停留在抽象规则，本轮至少应有以下脱敏样例：

1. 范围 + 条件进入 question
   - 输入：`我在高压力、信息不完整的时候做独立开发，通常会先快速试错，再决定要不要投入更多资源。`
   - 期望：至少有一条 question 体现“独立开发”语境与“高压力、信息不完整”条件
   - 期望：不能只抽成 `我的决策方式是什么样的？`

2. 术语语义进入主 question
   - 输入：`ReMi 对我来说不是聊天机器人，而是一个认知对齐的 AI 分身项目。`
   - 期望：主 question 不能只写 `我怎么看 ReMi？`
   - 期望：应显式说明 `ReMi` 是 AI 分身项目或同等语义对象

3. 定义锚点与判断锚点并存
   - 输入：`我说的 Ralph-Loop，就是目标会在预算允许下持续被唤起推进；我喜欢它，因为它不是做完一轮就停。`
   - 期望：必须输出至少 2 条锚点
   - 期望：其中 1 条回答 `Ralph-Loop 是什么`，另 1 条回答 `我为什么认可它`

4. 避免大而全 answer
   - 输入：`在工作协作里，如果压力大我会先追求推进；但如果是长期架构问题，我宁可慢一点先想清楚。`
   - 期望：必须输出 2 条锚点
   - 期望：两条锚点分别对应两个条件分支

5. 无历史依赖的负例
   - 输入：`我最近在做 XTP。`
   - 期望：若消息里没有定义句式或解释性短语，不得仅凭模型先验为 `XTP` 补定义锚点
   - 期望：最多只生成使用消息内已有语义的主锚点

## 验收标准

本轮完成后，应满足以下验收标准：

- 在给定样例中，question 必须显式包含至少一个边界要素（语境范围、成立条件、术语语义）
- 在术语样例中，主 question 不得只保留裸术语名
- 在样例 3 中，必须输出至少 2 条锚点，其中一条是术语定义锚点，另一条是判断锚点
- 在样例 4 中，必须输出 2 条锚点，分别对应两个条件分支
- 在样例 5 中，不得输出术语定义锚点
- 任何输出中的语境范围、成立条件、讨论对象补足、术语语义与定义锚点，都必须能在当前消息中找到对应文本证据
- 在样例 4 中，不允许产出 1 条同时覆盖两个条件分支的大锚点

## 总结

本轮不是把灵魂锚点从问答对升级成结构化对象，而是在保持 `question + answer` schema 不变的前提下，提升 question 的边界表达力与术语显化能力。

一句话概括：

> 访谈锚点提取要从“高召回事实抽取”升级为“高召回、自解释、术语显化的细粒度问答抽取”；核心手段不是拉长 answer，而是增加数量更多、边界更清晰、可按需召回的 question。
