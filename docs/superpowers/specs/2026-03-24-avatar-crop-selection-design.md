# 头像截取交互修复设计

## 背景

当前头像裁剪弹窗位于 `packages/web/src/components/profile/AvatarCropDialog.tsx`，导出逻辑位于 `packages/web/src/lib/avatar-editor.ts`。

现状交互是：用户只看到一个固定大小的裁剪视口，通过拖动图片内容和调节缩放，间接决定最终导出的区域。这个方向本身并非一定错误，但当前实现让图片主体在裁剪前难以完整感知，且预览与导出映射不够直接，导致用户难以稳定选中想要的头像区域。

用户确认并收敛后的设计意图是：

- 弹窗里必须能看到完整图片，允许被半透明遮罩弱化，但不能完全不可见
- 主交互可以采用成熟裁剪库常见的“拖动图片 + 固定裁剪框”模型
- 用户需要能通过 `Slider` 调整正方形裁剪范围大小
- 导出结果必须与当前可见裁剪框严格一致

## 问题定义

这次要修复的不是单一像素误差，而是当前裁剪体验与用户对“整图可感知、结果可预期”的设计意图不一致：

- 当前弹窗对完整图片的感知不足，用户难以判断主体是否被截断
- 用户明确接受“整图可见但被半透明遮罩覆盖”的成熟裁剪交互
- 导出逻辑若继续依赖分散的内部换算，仍然可能出现预览与导出不一致

因此本次修复目标是把交互模型和导出模型统一为“当前裁剪框即最终结果”，同时让完整图片在交互时始终可感知。

## 目标

- 在裁剪弹窗中让完整图片在初始态与最小缩放态完整可见；放大后框外区域仍需保留足够上下文，不能退化成“只剩裁剪框内容可见”
- 提供一个 `1:1` 正方形裁剪框
- 支持通过 `Slider` 调整裁剪范围大小
- 导出结果与选择框严格一致
- 保持现有弹窗流程、上传流程和服务端接口不变

## 非目标

- 不修改头像上传 API
- 不在本次修复中加入旋转、非正方形裁剪、多选框等扩展能力
- 不重做设置页其余 UI
- 不把“拖边/拖角直接缩放”作为本次必须交付能力

## 方案对比

### 方案 A：引入成熟裁剪库，保留现有弹窗与上传管线（推荐）

- 使用 `react-easy-crop` 提供“整图可见 + 半透明遮罩 + 固定裁剪框 + 图片拖动/缩放”交互
- 通过外部 `Slider` 驱动裁剪范围缩放
- `avatar-editor` 导出接口改为接收最终裁剪区域在原图坐标系中的区域
- 上传、成功/失败提示、文件校验逻辑保持不变

优点：

- 最符合用户已确认的交互偏好
- 使用成熟库降低移动端触控与边界处理风险
- 改动集中在前端裁剪层与导出层

缺点：

- 需要引入额外依赖并适配现有样式与测试

### 方案 B：自研“拖动图片 + Slider 缩放”裁剪层

- 自己实现完整图片显示、遮罩、裁剪框、拖动与缩放映射
- 导出层同样接收显式裁剪区域

优点：

- 无外部依赖，可完全按本项目风格定制

缺点：

- 触控边界、坐标映射和测试成本更高
- 对边缘功能来说维护性不如成熟库

### 方案 C：继续沿用当前实现，只修正坐标换算

优点：

- 改动最小

缺点：

- 仍无法解决“完整图片不可感知”的问题
- 只是修补症状，不足以保证体验达标

## 推荐方案

采用方案 A。

原因：用户已经明确接受成熟库常见的“整图可见但框外弱化、拖动图片配合缩放”的交互，只要求完整图片不能完全不可见。`react-easy-crop` 的交互范式和移动端触控成熟度都适合这类边缘功能；真正需要严控的是导出坐标必须直接基于库输出的裁剪区域，而不是再走一层不透明的旧换算。

## 交互设计

### 弹窗显示

- 弹窗中央展示完整图片，按容器等比缩放
- 图片上方覆盖半透明蒙层
- 中央出现一个固定比例为 `1:1` 的正方形裁剪框
- 裁剪框内部代表最终导出范围，框外区域通过遮罩弱化，但底图仍需清晰可感知

### 用户操作

- 用户主操作是拖动图片位置，以改变裁剪框中的取景内容
- 用户通过 `Slider` 调整裁剪范围大小
- 本次不要求拖边/拖角直接缩放；如库默认附带该能力，可不对外暴露为主交互
- 所有交互都必须实时限制在图片可选范围内

### 初始裁剪规则

- 初始取景位置为图片中心
- 初始缩放必须让整张图片完整可见
- 对应到库配置时，初始 crop/zoom 必须是确定性的，不依赖浏览器偶然布局结果

### 缩放策略

- 本次保留缩放能力，并以 `Slider` 作为主控件
- `Slider` 改变的是图片相对于固定裁剪框的缩放级别：向右 = `zoom` 增大 = 有效裁剪范围变小
- `minZoom` 必须对应“初始态 / 整图完整可见”
- 默认值为 `minZoom`
- `maxZoom` 由图片边界与可用交互范围共同决定，但必须保证不会裁出图片边界之外的区域
- 非最小缩放态允许图片局部超出可视区域，但框外仍必须保留当前图片上下文，不能视觉上退化为“只剩框内内容可见”

## 数据与导出模型

### 新的裁剪数据模型

裁剪状态以库输出的原图坐标裁剪区域作为导出前的唯一真实来源。界面内部可以维护 `crop` 与 `zoom` 作为交互态，但最终导出必须使用库提供的像素级裁剪区域。

导出层不再基于旧的 `crop.x/y + zoom + cropSize` 自行反推源区域，而是直接消费一个明确的正方形区域：

- 原图坐标系中的 `x`
- 原图坐标系中的 `y`
- 原图坐标系中的 `width`
- 原图坐标系中的 `height`

这表示“从原图的哪个像素区域截取”。对于 `1:1` 裁剪框，`width` 与 `height` 预期应相等或只存在不超过 `1px` 的取整差异。

### 导出规则

- `exportCroppedAvatar` 直接使用该区域执行 `drawImage`
- 输出目标尺寸保持当前行为不变，继续导出为固定方形头像位图（当前调用方仍使用 `512 x 512`）
- 输出格式仍为 WebP
- 继续保留质量/尺寸递减以满足上传体积限制
- 导出区域必须直接来自 `react-easy-crop` 的 `croppedAreaPixels`
- 导出前只允许做一次统一的 `round + clamp`，不允许继续通过旧的视口偏移模型间接推导

### 边界不变量

所有交互与导出前都必须满足：

- `0 <= x`
- `0 <= y`
- `x + width <= imageWidth`
- `y + height <= imageHeight`

这些限制应在交互过程中实时生效，而不是只在确认导出时兜底。

### 小图规则

- 对于小于目标导出尺寸的图片，不拒绝上传
- 仍允许从原图中选择最大可用正方形区域，再由现有导出流程放大到目标输出尺寸
- 本次不新增“小图不可上传”的额外校验

## 组件改动

### `packages/web/src/components/profile/AvatarCropDialog.tsx`

- 接入 `react-easy-crop`
- 明确库配置至少包含：`aspect=1`
- 使用等效于 `objectFit="contain"` 的配置，保证初始态与最小缩放态整图完整可见
- 启用位置限制，避免拖动后出现可裁出图片外空白区域的情况
- 使用固定 `1:1` 裁剪框，显示完整图片与半透明遮罩
- 维护库所需的 `crop` / `zoom` 交互态，并通过 `Slider` 控制 `zoom`
- 在 `onCropComplete` 一类回调中拿到原图坐标系裁剪区域 `croppedAreaPixels`
- 确认按钮点击后，将最终裁剪区域传给导出层
- 不继续复用旧的中心点反推逻辑

### `packages/web/src/lib/avatar-editor.ts`

- 将源区域解析逻辑改成直接消费显式裁剪矩形
- 保留文件类型校验、WebP 导出、尺寸与质量回退机制
- 删除或简化与旧实现耦合的二次坐标换算

## 测试策略

### 单元测试

在 `packages/web/test/lib/avatar-editor.test.ts` 中补充或调整测试：

- 给定明确原图裁剪区域时，导出使用该区域而非中心反推
- 导出区域被正确映射为 `drawImage` 的源参数
- 仍然保留体积压缩与失败路径测试
- 覆盖横图、竖图、四角边界区域
- 覆盖小图输入仍可正常导出

### 组件测试

为 `AvatarCropDialog` 增加测试，覆盖：

- 打开后完整图片在遮罩下仍可见，不出现“只剩截取区域可见”的旧体验
- 默认取景位于图片中心
- 拖动图片后，确认导出对应区域发生变化
- 调整 `Slider` 后，确认导出区域大小发生预期变化；`Slider` 向右时导出区域变小
- 横图和竖图都能正确映射裁剪区域
- 连续拖动和缩放后，导出区域仍与当前裁剪框一致，允许不超过 `1px` 的取整误差

### 浏览器级验收

- 使用固定横图与竖图样例，在真实浏览器环境执行拖动 + `Slider` 缩放 + 导出
- 断言最终导出位图与预期 crop 区域一致，允许不超过 `1px` 的 rounding tolerance
- 这类验证用于覆盖 jsdom 难以准确证明的视觉与坐标联动风险

## 验收标准

- 用户在裁剪弹窗中能看到完整图片
- 用户可以通过拖动图片与 `Slider` 缩放来选择头像截取范围
- 最终上传的头像与当前裁剪框一致；对于测试用固定图片，导出的源区域应与库输出的原图裁剪区域一致，允许不超过 `1px` 的 rounding tolerance，不接受旧模型那种中心反推偏差
- 现有 PNG/JPEG/WebP 校验逻辑不回退
- 现有上传大小限制逻辑不回退
- 对横图、竖图、小图都满足相同裁剪规则

## 风险与应对

- 显示坐标到原图坐标映射容易出错
  - 应对：只信任库输出的像素裁剪区域，避免自己重复推导
- 拖拽边界容易出现一像素级抖动
  - 应对：以库的边界行为为主，并在导出层对最终像素区域做一次显式钳制
- `Slider` 与库内部 `zoom` 范围若定义不清，容易让缩放体验失控
  - 应对：在实现时固定最小/最大 zoom 规则，并用测试覆盖最小值、最大值和中间值

## 实施顺序

1. 先为导出层写失败测试，锁定“显式裁剪区域即导出区域”
2. 改造 `avatar-editor.ts` 的输入模型和导出逻辑
3. 为 `AvatarCropDialog` 写失败测试，锁定整图显示、拖动图片与 `Slider` 缩放交互
4. 用 `react-easy-crop` 重写 `AvatarCropDialog.tsx` 的交互实现
5. 跑相关测试并修正边界问题
