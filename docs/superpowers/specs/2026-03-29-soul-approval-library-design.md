# 统一灵魂锚点审批库与审批中心设计

## Executive Summary

- 所有来源产生的锚点/探针都必须先进入统一候选审批库，不能再直写正式资产
- 候选库是待处理队列，不是审计系统；候选一旦处理完成即删除
- 正式层继续统一存储灵魂锚点与灵魂探针，`answer` 归一化后为 `null` 视为探针，否则视为锚点
- 底部导航主入口升级为 `审批中心`，并以 mobile-first 的手势审批为主交互
- 审批中心通过 path 表达状态：`/approval/anchors` 与 `/approval/probes`，UI 以两个 tab 呈现，二者一一映射
- 快速手势只覆盖可直接完成的审批；凡涉及“更新已有资产”，必须进入详情页显式选择目标后再提交
- `下滑撤销` 首版只支持服务端 `last_action` 单步撤销，短 TTL、非审计历史
- 本轮不做审批历史、自动查重、自动合并、复杂版本管理；先把“统一审批收口”做成稳定闭环

## 概述

当前 ReMi 的产品定义已经明确要求：所有锚点与探针都应经过用户审批后，才能进入正式灵魂资产库。但现有流程中，部分来源仍然可能直接落入正式锚点库，导致审批门控没有真正成为统一系统边界。

本设计的目标，是把所有锚点/探针候选统一收口到一个异步审批入口，并为人类用户建立一个 mobile-first 的审批中心。审批中心不仅用于“通过或拒绝”，还应允许用户对候选与正式资产进行灵魂微调，并支持把已有锚点通过灵魂否认降级为探针。

本轮重点解决三件事：

- 所有来源统一改成“先进入候选审批库，再异步人工审批”
- 审批动作标准化，明确锚点、探针、丢弃三种流向
- 设计一个以审批为主轴的移动端审批中心 UI，而不是把审批塞进已有页面角落

## 背景问题

### 1. 审批边界不统一

当前系统的概念边界已经是“高质量候选 -> 人类审批 -> 正式资产”，但工程路径还没有完全收口。只要还有任一入口能绕过审批直接写正式锚点库，审批就只是局部能力，而不是全局原则。

### 2. 锚点与探针流程虽然概念统一，但产品操作还不统一

从产品定义上，灵魂探针就是“无答案的灵魂锚点参考形式”。这意味着两者本质上是同一种灵魂资产在不同完成度下的形态。问题在于，如果审批阶段仍然分裂成多套候选对象、多套路由、多套结果语义，用户就会被迫理解不必要的复杂性。

### 3. 移动端缺少高效审批工作台

ReMi 面向 mobile-first PWA。审批动作又是高频、重复、强语义的操作。如果沿用桌面分栏思路，审批会显得笨重；如果没有快速手势与明确的预提交语义反馈，用户又容易误操作。

## 目标

- 任意来源产出的锚点/探针候选，都必须先进入统一候选审批库
- 审批完成后，候选应立即流转并从候选库删除，不保留审批历史
- 正式层统一存储灵魂锚点与灵魂探针，不拆成两套存储结构
- 通过 `answer` 是否为空区分正式资产是锚点还是探针
- 支持 `灵魂微调` 与 `灵魂否认` 两类人工干预动作
- 提供独立的移动端 `审批中心` 主入口，并以审批为产品主轴

## 非目标

- 本轮不做审批历史审计
- 本轮不做自动查重、自动合并、自动冲突解决
- 本轮不做复杂版本管理或回滚历史
- 本轮不强制建立候选与正式资产之间的永久追踪关系
- 本轮不分离锚点与探针存储，也不把正式资产的 `answer` 改成 `NOT NULL`

## 备选方案

### 方案 A（采用）：统一候选库 + 统一正式资产库 + 审批中心

- 所有来源统一进入候选库
- 正式层统一存储锚点与探针
- 审批中心成为移动端主入口

选择原因：最符合当前产品概念，也最容易支持探针补全、锚点降级、灵魂微调。

### 方案 B（放弃）：统一候选库 + 分离正式锚点/探针存储

- 候选层统一
- 正式层拆成锚点表与探针表

放弃原因：会把 `answer` 空/非空这一单一语义差异放大成跨表迁移，导致探针补全、灵魂否认、查询与维护都更复杂。

### 方案 C（放弃）：候选事件流 + 资产聚合层

- 每次候选与审批都记录成事件
- 正式资产由聚合器计算得到

放弃原因：审计性最强，但远超本轮需要的复杂度，不适合优先解决“统一异步审批入口”。

## 设计决策

| 决策项        | 选择                                             | 理由                                         |
| ------------- | ------------------------------------------------ | -------------------------------------------- |
| 候选层        | 统一候选审批库                                   | 所有来源统一收口，先审批再入正式资产         |
| 正式层        | 统一灵魂资产库                                   | 锚点与探针只差 `answer` 是否存在，不需要拆表 |
| 锚点/探针区分 | `answer != null` 为锚点，`answer == null` 为探针 | 与产品概念完全一致，升级/降级都是普通更新    |
| 候选保留策略  | 审批后直接删除                                   | 候选库是工作队列，不是审计账本               |
| 冲突处理      | 第一版不自动处理                                 | 避免过早做语义合并，降低误伤                 |
| 更新已有资产  | 人工明确选择更新目标                             | 允许对已有问题做补充或修正                   |
| 主 UI 入口    | 底部导航中间的 `审批中心`                        | 将人类审批门控提升为产品主轴                 |
| 审批中心结构  | 一个中心 + 两个 path/tab                         | 统一入口，区分锚点审批与探针审批语义         |

## 核心对象模型

### 候选审批项

候选审批项是所有来源的统一入口。每条候选至少包含以下字段：

- `id`
- `question`
- `answer?`
- `source`
- `sourceRef`
- `createdAt`

约束：

- `question` 必须存在
- 持久化前必须对 `question` 执行 `trim`
- `question` 在 `trim` 后若为空，则拒绝写入候选库或正式层
- `answer` 可为空
- 持久化前必须对 `answer` 执行归一化：`trim` 后若为空字符串，则统一写为 `null`
- `answer` 归一化后为 `null` 时，它是候选探针
- `answer` 归一化后不为 `null` 时，它是候选锚点

候选审批项不承担长期留存职责。它存在的唯一目的，是等待用户处理。

### 正式灵魂资产

正式灵魂资产是审批后的统一沉淀层。至少包含：

- `id`
- `question`
- `answer?`
- `createdAt`
- `updatedAt`

正式层不物理区分锚点与探针，而只通过归一化后的 `answer` 语义判断：

- `answer != null` -> 灵魂锚点
- `answer == null` -> 灵魂探针

这使以下动作都成为普通更新，而不是跨库迁移：

- 探针补全为锚点
- 锚点通过灵魂否认降级为探针
- 用户直接灵魂微调 `question / answer`

## 候选来源原则

任意会产出锚点/探针的流程，都只能产出候选审批项，不能直接写正式资产。

包括但不限于：

- `interview`
- `reading`
- `reasoning` 过程中暴露的信息缺口、新发现或建议补充
- 未来任何新的感知入口

这条原则是系统级约束：所有灵魂锚点与灵魂探针，都必须经过用户审批。

## 审批流转语义

### 候选库定位

候选库不是状态机账本，而是待处理队列。

- 候选进入后，处于待审批状态
- 一旦用户完成处理，候选立即从候选库删除
- 系统不保留审批历史

### 标准审批结果

每次审批只关心“认可范围”和“流转落点”。

认可范围固定为三种：

1. 认可 `question + answer`
2. 只认可 `question`
3. `question` 和 `answer` 都不认可

对应流转结果：

- 认可 `question + answer`：写入或更新正式资产，结果为锚点
- 只认可 `question`：写入或更新正式资产，结果为探针
- 都不认可：不写正式资产，直接删除候选

补充说明：

- 探针页中的“暂时保留探针”不是审批结果，而是**非提交动作**
- 它的含义仅是：跳过当前卡片、保留在候选队列中、稍后再看
- 因为它不构成审批，所以不会删除候选，也不会写正式资产

### 更新已有资产

系统必须允许候选完全使用与已有正式资产相同的 `question`，并将其视为对已有资产的补充更新，而不是冲突。

第一版规则：

- 系统不自动判重或自动拦截
- 用户可以显式选择“新建正式资产”或“更新已有正式资产”
- `question` 完全相同的候选，可以用于修正、补充或替换既有资产内容
- 即使用户判断其与现有问题接近或重复，首版仍允许选择“新建正式资产”；是否重复由人工承担判断责任

额外约束：

- 快速手势只处理“无需选择更新目标即可完成”的审批
- 凡涉及“更新已有资产”，必须进入详情页后，由用户显式选择目标资产再提交
- 首版不在手势层做自动匹配已有资产或中途弹出更新选择器

## 人工干预动作

### 灵魂微调

`灵魂微调` 指人工直接修改 `question / answer`。

它可以发生在两个位置：

- 审批前：直接修改候选内容，再执行审批流转
- 审批后：直接修改正式灵魂资产内容

灵魂微调是审批中心的基础能力，因为很多候选并不是“对”或“错”，而是“接近可用但需要人类修正”。

### 灵魂否认

`灵魂否认` 指保留 `question`，但明确否认当前 `answer`，使已有锚点降级为探针。

数据语义为：

- 保留原 `question`
- 将 `answer` 置空

灵魂否认是正式资产层动作，不要求一定通过候选流转触发。它应当可以在资产详情中单独执行。

## 事务、幂等与并发语义

### 审批提交

`approve(candidateId, action)` 必须是原子操作：

- 写入或更新正式资产
- 删除候选

两步要么同时成功，要么同时失败，不允许出现“资产已写入但候选未删除”或“候选已删除但资产未落库”的中间态。

### 审批幂等

审批接口必须支持幂等重试。最小要求：

- 同一 `candidateId + requestId` 的重复提交只能生效一次
- 网络重试或客户端重复点击不能重复创建正式资产

### 并发审批

同一候选若被多个客户端同时处理，系统应只接受第一个成功提交的审批，其余提交返回“候选已处理”。

### 更新已有资产的并发保护

凡是“更新已有资产”的提交，都必须携带目标正式资产的版本号或 `updatedAt`。

- 仅当目标资产版本未变化时，才允许更新
- 若目标资产在用户打开详情后已被其他审批、灵魂微调或灵魂否认修改，则本次提交返回“目标资产已变化，请重新确认”
- 版本校验属于审批事务前置条件；若校验失败，则本次审批整体失败，候选保持待处理、不写正式资产、不记录 `last_action`

首版采用乐观并发控制，不引入复杂锁模型。

### 撤销边界

`last_action` 必须至少按用户维度隔离，不能是全局单槽。

`undo(actionId)` 仅允许撤销：

- 该用户最近一次成功审批动作
- 且目标正式资产在该动作之后未被再次修改

若目标资产已被后续编辑、灵魂微调或再次审批影响，则撤销应明确失败，而不是尝试做级联回滚。

## 标准流程

### 上游提交流程

任意来源生成候选时：

1. 构造候选审批项
2. 写入候选审批库
3. 不直接改动正式资产

由于统一改成异步审批，上游候选生成条件可以相对放宽，优先保证“先进入候选池，再由用户筛选”。

## 统一写入门禁

灰度迁移之前，必须先建立正式资产统一写入门禁：

- 正式资产不存在“审批写接口 vs 其他写接口”的分裂模型，而只允许通过一个统一受控写服务/门禁落库
- 审批提交、正式资产灵魂微调、灵魂否认、撤销回滚都只能作为不同 action 走同一个受控写服务
- 所有非审批路径对正式资产的直接写入都必须被拒绝或重定向为候选入库
- 任何服务、页面、脚本都不得直写正式资产表

所有进入正式层的写操作，不论 action 为 `approval`、`update_existing`、`micro_edit`、`deny`、`undo`，都必须先经过同一套归一化管线：

- `question.trim`
- 空白 `question` 直接拒绝
- `answer.trim` 后若为空字符串，则统一写为 `null`

归一化完成后，系统必须基于归一化后的 `answer` 统一重算：

- 资产类型（锚点 / 探针）
- 对应 path/tab 归属
- 相关查询索引与统计口径

因此，灰度迁移的对象是“各来源如何接入候选库”，而不是“是否继续允许旧路径绕过审批”。系统边界必须先封死，再逐步迁移来源。

### 用户审批流程

用户处理单个候选时，标准动作顺序为：

1. 查看 `question`、`answer` 与 `source` 上下文
2. 必要时执行 `灵魂微调`
3. 选择认可范围：`question + answer` / `只认可 question` / `都不认可`
4. 如需保留，选择 `新建正式资产` 或 `更新已有正式资产`
5. 执行流转
6. 从候选库删除该候选

### 正式资产维护流程

用户处理正式资产时，支持：

- `灵魂微调`
- `灵魂否认`
- 基于新候选更新已有资产

## UI 信息架构

### 产品主入口

审批不是附着在发现页中的一个次级功能，而是独立工作台。

本轮建议将底部导航栏中间项设置为 `审批中心`，并允许它成为人类用户每次打开产品时优先看到的首页入口。

### 审批中心路由

审批中心使用两个 path 来表达 tab 状态：

- `/approval/anchors`
- `/approval/probes`

路由直接承载 path 状态，UI 层以 tab 呈现，二者一一映射。好处是：

- 刷新后可恢复当前 tab
- 返回导航更稳定
- 可直接深链访问具体审批页
- “记住上次停留位置”天然由最近访问 path 实现

所有候选的类型判定、tab 分流与动作可用性，都以后端归一化后的 `answer` 结果为准；任何灵魂微调保存后，都必须重新计算候选或正式资产的归属。

进入审批中心时：

- 若存在最近访问 path，则直接返回上次所在 tab；该记录按用户维度持久化
- 否则使用默认 path `/approval/anchors`

## 审批中心页面设计

### 总体原则

- mobile-first
- 单手可操作
- 快速审批与精细编辑分离
- 手势动作高频，但必须可理解、可撤销、可预览

### Tab 结构

审批中心包含两个 tab，但两者共享统一候选来源与数据内核：

- `灵魂锚点`：处理 `answer != null` 的候选
- `灵魂探针`：处理 `answer == null` 的候选

虽然存储层统一，但产品层必须拆开两个审批视图，因为两边的审批语义不同。

### 主交互：手势快速审批

#### 灵魂锚点审批页

- `右滑`：认可 `question + answer`
- `左滑`：只认可 `question`
- `上滑`：丢弃
- `下滑`：撤销上一步

#### 灵魂探针审批页

- `右滑`：认可探针
- `左滑`：暂时保留探针（非提交动作，仅跳过）
- `上滑`：丢弃
- `下滑`：撤销上一步

两个 tab 共享同一套手势骨架，但不共享完全相同的业务语义。尤其左滑动作，必须根据当前 tab 改变文案、图标与高亮色，避免用户混淆。

### 点按进入详情页

手势只负责快速处理。任何精细动作都应通过点按卡片进入详情页完成。

详情页至少支持：

- 查看来源上下文
- `灵魂微调`
- 选择更新已有资产

审批中心中的候选详情页只处理候选，不直接承担正式资产管理。若用户要编辑正式资产，应跳转到独立的正式资产详情页。

正式资产详情页至少支持：

- `灵魂微调`
- `灵魂否认`

### 手势语义提示动画

所有滑动动作，在用户松手提交前，都必须配合明确的语义提示动画。

这是强约束，不是视觉润色。动画至少包含三类反馈：

1. `方向反馈`：卡片随手势位移、倾斜
2. `结果反馈`：明确显示当前将要执行的动作文案，如“认可锚点”“只留问题”“认可探针”“暂时保留探针”“丢弃”“撤销上一步”
3. `阈值反馈`：未达到阈值时是预览态，达到阈值后进入“松手即提交”态

额外要求：

- 不能只靠颜色传达语义，文案必须出现
- `下滑撤销` 必须明确提示“撤销上一步”，避免被误解为刷新或展开详情
- 第一版撤销只做单步撤销，不做复杂多级历史回退

### 撤销机制

为兼容“候选处理后立即删除”与“需要单步撤销”，服务端允许维护一个短 TTL 的 `last_action` 临时缓冲：

- 只保留最近一次已提交审批动作
- 只保留短时间窗口，用于立即撤销
- 该缓冲不是审批历史，也不提供列表查询
- 撤销成功后，应回滚最近一次正式资产写入，并将对应候选放回候选队列

首版不支持跨多步回退，不支持长期恢复已处理候选。

## 查询与视图规则

正式资产层的底层存储统一，但查询与 UI 视图按 `answer` 是否为空分流：

- 锚点页、锚点召回、锚点统计 -> `answer != null`
- 探针页、探针浏览、探针调度 -> `answer == null`

候选审批页也按同样规则分配到对应 tab：

- 有 `answer` 的候选进入 `anchors`
- 无 `answer` 的候选进入 `probes`

## 迁移、灰度与回滚

### 迁移原则

- 现有任何能直接写正式资产的来源，都必须逐步收口到候选审批库
- 收口优先级建议从单一来源开始，逐步扩展到全部来源
- 正式层 schema 本轮不拆表，只补足 `answer` 归一化约束

### 灰度顺序

1. 先上线正式资产统一写入门禁
2. 再上线候选审批库与单一来源接入
3. 再上线审批中心 UI 的最小可处理入口
4. 若首批来源会同时产出锚点候选与探针候选，则必须同时提供两类候选的可处理入口；否则首批来源必须限制为只产出当前 tab 已覆盖的候选类型
5. 再接入第二个 tab 与剩余来源
6. 最后移除所有旧直写实现代码

发布门槛：任何新接入来源上线前，必须证明其产出的候选类型都有对应可处理入口；否则禁止放量。

### 回滚原则

- 可以临时下线审批中心 UI 或单个来源接入
- 但不允许恢复新的“绕过审批直写正式层”路径
- 若灰度失败，应保留候选入库能力，暂停审批展示或暂停新增来源接入，而不是回到无审批门控的旧模型

## 可观测性

为验证“所有来源都先过审批”，至少需要以下事件或计数：

- `candidate_created`：按 `source` 统计候选生成次数
- `approval_applied`：按动作类型统计审批提交次数
- `approval_committed`：统计审批事务成功提交次数
- `approval_rolled_back`：统计审批事务回滚次数
- `candidate_skipped`：统计探针页“暂时保留探针”的跳过次数
- `candidate_deleted`：统计候选被成功消费删除的次数
- `candidate_restored`：统计候选因撤销被恢复的次数
- `direct_write_blocked`：统计旧路径被拦截的次数
- `undo_applied`：统计单步撤销次数
- `formal_asset_written`：记录每一次正式资产写入，并带上 `gateway=controlled_write_service` 与 `actionType=approval | update_existing | micro_edit | deny | undo | other`
- `approval_rejected_already_processed`：统计候选已处理冲突
- `approval_rejected_stale_target`：统计更新已有资产时的目标版本冲突
- `approval_idempotency_hit`：统计幂等命中次数
- `undo_rejected_conflict`：统计因目标已变化而撤销失败的次数
- `approval_tx_failed`：统计审批原子事务失败次数

最小排障目标：能够回答“某个来源今天是否仍在尝试绕过审批库”“候选是否成功进入对应 tab”“撤销是否异常偏高”。

额外告警约束：

- 任何 `gateway != controlled_write_service` 或 `actionType = other` 的 `formal_asset_written` 都视为系统边界破坏，应触发告警
- 一次 `approval_applied` 成功后，必须能关联到且仅关联到 1 次 `formal_asset_written` 与 1 次 `candidate_deleted`；否则触发告警
- 一次成功 `undo_applied` 后，必须能关联到且仅关联到 1 次 `candidate_restored` 与对应的正式资产回滚；否则触发告警

## Milestones

### Milestone 1：最小审批闭环

- 接入一个来源
- 候选库上线
- `/approval/anchors` 上线
- 支持 `认可 question + answer` / `只认可 question` / `丢弃`

### Milestone 2：探针审批与撤销

- `/approval/probes` 上线
- 支持探针页左滑跳过、下滑单步撤销
- 支持 `answer` 归一化与锚点/探针稳定分流

### Milestone 3：精细编辑能力

- 候选详情支持 `灵魂微调`
- 详情页支持“更新已有资产”
- 正式资产详情支持 `灵魂否认`

## 数据约束与迁移结论

本轮不分离灵魂锚点与灵魂探针存储。

因此：

- 不新增独立探针表来替代现有灵魂资产表
- 不将现有正式资产的 `answer` 改成 `NOT NULL`
- 正式层继续允许 `answer` 为空

这是本轮的明确设计决策，而不是暂时未实现的缺口。

## 风险与取舍

### 1. 不保留审批历史的取舍

优点是对象模型简单、实现轻、移动端操作心智清楚。代价是无法追溯候选为何被拒绝或降级。本轮接受这一取舍。

### 2. 不自动处理重复的取舍

优点是避免语义误伤，也与当前“先统一审批流程”目标一致。代价是正式资产可能存在重复或接近重复问题。本轮通过人工选择“更新已有资产”来缓解，而不是试图自动解决。

### 3. 审批中心成为首页的取舍

优点是把人类审批门控提升为产品主轴。代价是产品首页不再首先展示发现或聊天能力。但这与 ReMi 当前阶段“先把灵魂资产质量做对”的方向一致。

## 验收标准

- 所有锚点/探针来源都无法绕过候选审批库直接写正式资产
- 正式资产写入统一经过审批写接口，任何非审批写入都会被拒绝或告警
- 候选审批完成后，会立即从候选库移除
- `question` 在持久化前会做 `trim`，空白问题会被拒绝
- 正式层中，`answer == null` 的资产可以被系统稳定视为探针
- `answer` 在持久化前会做统一归一化，空白字符串会写为 `null`
- 用户可以在审批前后执行 `灵魂微调`
- 用户可以对正式锚点执行 `灵魂否认`
- 移动端存在独立 `审批中心` 主入口
- 审批中心路由为 `/approval/anchors` 与 `/approval/probes`
- 两个 tab 的手势语义符合本设计定义，且松手前均有明确语义提示动画
- 任何“更新已有资产”的动作都不会通过快速手势直接完成，而必须进入详情页显式选择目标
